---
title: The Hikari command
description: Reference for the Hikari server management command.
---

Running `hikari` with no arguments opens a menu in the terminal: status, updates, logs, access, REALITY sites, nodes, backups. The same actions are available as commands. Run them as root.

## Server

| Command | What it does |
|---|---|
| `hikari status` | containers, CPU and memory, panel state, available update |
| `hikari doctor [--json]` | check the panel's or node's server, a hint on every line, see below. `--json` prints the report as JSON, secrets cut out |
| `hikari support <code> [--dry-run]` | send support the check, the status and the last log lines (secrets cut out) with the code from your ticket, see below |
| `hikari logs [panel\|node]` | live logs, <kbd>Ctrl</kbd>+<kbd>C</kbd> stops |
| `hikari restart` | restart the containers |
| `hikari support-access on\|off` | allow or forbid [support access](/Hikari/en/operations/support-access/) on this server; `off` holds whatever the panel says |
| `hikari update [--check]` | update now, a backup first, rollback on failure. `--check` only checks |
| `hikari install [flags]` | install; on an installed server it opens the menu |
| `hikari uninstall [-y]` | stop and remove the command, data stays in `/opt/mikan` |

`hikari doctor` works on a panel's server and on a node's server. It checks Docker and the containers, that the ports are listening, ufw rules for the node API port, the panel port and the protocol ports, time sync (`timedatectl` and the HTTP Date header from github.com, 30 s tolerance), DNS, outbound HTTPS to github.com and ghcr.io (needed for updates), disk (✗ under 500 MiB, ! under 2 GiB) and memory. On a node it also re-sends the hello to the panel and prints the result. Each line is marked ✓, ! or ✗ and has a fix line; if anything is ✗, the command exits with a non-zero code. `hikari status` suggests `hikari doctor` when something is wrong. This is the tool for when the panel cannot reach the node at all. The same set of checks for the panel's server is in the panel itself: the "Check server" button in **Settings → System**.

The panel runs `hikari doctor` and `hikari restart` on its own server, and on a node's server over the node API, without SSH: it writes a request file into its data directory and a systemd unit (`hikari-doctor-request.path`, `hikari-restart-request.path`, installed by the installer and by `hikari update`) runs the command and returns the report. A server installed before 0.5.1.1 needs one `hikari update` for that. The logs of the panel and of the nodes are shown in the panel as well, with tokens, keys, passwords and subscription links cut out. All of it is on the [Diagnostics](/Hikari/en/operations/diagnostics/) page.

`hikari support <code>` is for the case when the panel is down or the node is out of the panel's reach. Take the code from your support ticket, run the command as root: it collects the same report as `hikari doctor --json`, `hikari status` and the last 300 lines of the containers' logs, cuts the secrets out and sends one JSON document to the support desk (`MIKAN_SUPPORT_URL` points it elsewhere). `.env`, keys and certificates are not read and not sent. `--dry-run` prints what would be sent and sends nothing.

## Access

| Command | What it does |
|---|---|
| `hikari url` | the panel link and login |
| `hikari reset-password` | a new administrator password, all sessions and API keys are revoked |
| `hikari reset-path` | a new secret link, the old one stops working |
| `hikari disable-2fa` | turn off 2FA if the phone is lost |

## Backups

| Command | What it does |
|---|---|
| `hikari backup` | a backup into `/opt/mikan/backups` |
| `hikari restore FILE [-y] [--no-db-snapshot]` | restore from a backup, see [Backups](/Hikari/en/operations/backups/) |

## Nodes and connections

| Command | What it does |
|---|---|
| `hikari node list` | the panel's nodes |
| `hikari node add --name NAME --host IP [--domain D] [--api-port P]` | add a node and get a key |
| `hikari node key NODE` | a new node key, the old one stops working |
| `hikari node set NODE [--name] [--host] [--domain] [--enabled=true\|false]` | change a node |
| `hikari join [KEY] [--panel-ip IP]` | on a node: accept a new key from the panel |
| `hikari inbound list` | connections |
| `hikari inbound add PRESET [--port PORT] [--node N]` | add a connection; without a preset it shows the list |
| `hikari inbound set NAME --port PORT [--node N]` | change the port, keys and masking stay |

The panel's own node has number 1, and its address and domain are changed in the panel settings.

## Certificates

| Command | What it does |
|---|---|
| `hikari cert set --cert fullchain.pem --key privkey.pem [--node N]` | your own certificate for the panel or a node |
| `hikari cert show [--node N]` | what is installed now |
| `hikari cert clear [--node N]` | go back to the automatic certificate (for a node: self-signed) |
| `hikari cert proxy <domain>` | nginx or Caddy holds port 80: pass the certificate authority's checks through it to the panel or node (the rule is backed up, the config tested and reloaded) |

## REALITY masking sites

| Command | What it does |
|---|---|
| `hikari targets scan [--node N] [--json]` | find suitable sites near the server |
| `hikari targets check --dest HOST:PORT [--sni NAME]` | check a site |
| `hikari targets apply --dest HOST:PORT [--sni NAME] (--all \| --inbound NAME) [--force]` | set the site for all connections or for one |

For an IP address in `--dest`, `--sni` is required. The site is checked before it is applied, and `--force` skips the check.

## Payment adapters

| Command | What it does |
|---|---|
| `hikari addon list` | what is running and what is in the catalog |
| `hikari addon install ID` | install or update an adapter |
| `hikari addon remove ID` | stop and remove, settings and payments in the panel stay |
